# Exercise Demonstration Images

## What this is

48 of the app's 61 bundled exercises (`assets/data/exercises.json`) ship two real
demonstration photos each (start/end position), shown as a crossfading
pseudo-animation in `ExerciseDetailCard`. The other 13 — the ones
free-exercise-db had no safe match for — each ship one male and one female
demonstration photo from Pexels instead (see "Gendered photos" below), shown as
a single static image picked by the user's profile sex.

## Why static photos, not GIFs

The original ask was animated GIFs. Every freely-downloadable GIF source found
during research turned out to be unusable for permanent self-hosting:

- **ExerciseDB (exercisedb.io)** — the only large (1300+ exercise) GIF dataset —
  is a paid API product. Its free tier is rate-limited, request-time-only access;
  the terms do not grant bulk-download-and-rehost rights, which is exactly what
  permanently self-hosting the media under our own storage would require.
- Other GitHub "exercise GIF" repos either wrap the same ExerciseDB media (same
  licensing problem, one level removed) or are AGPL-3.0-licensed **code** with no
  explicit license covering the **media assets** themselves — a code license does
  not imply redistribution rights for the images/GIFs it happens to serve.

Bulk-downloading and rehosting any of these would have violated the task's own
explicit constraint: "Do not bypass authentication, paywalls, access controls, or
licensing restrictions." This was surfaced to the user as a genuine blocking
conflict (self-hosting GIFs permanently vs. not violating licensing — the task's
own steps 3 and 5 were in tension for every available GIF source), and the user
chose the legally clean alternative.

**Decision (user-approved): use [free-exercise-db](https://github.com/yuhonas/free-exercise-db)
(Unlicense — public domain) instead.** It has no licensing risk at all, but only
ships static JPEG photos per exercise (typically 2, framing the start/end of the
rep), not GIFs. That's the deviation from the original spec: real demonstration
media, honestly labeled as photos rather than animated GIFs.

## Why bundled assets, not cloud storage

The project has no Supabase Storage bucket configured (`supabase storage ls`
returns an empty bucket list), and per [OFFLINE_FIRST.md](OFFLINE_FIRST.md) the
app must never depend on the network for core functionality — including viewing
an exercise's demonstration media mid-workout, possibly offline at a gym. Adding
a storage bucket and a fetch-and-cache path would have introduced exactly the
network dependency that principle rules out, for no real benefit at ~6MB total.
So the 96 images are bundled as ordinary Flutter assets
(`assets/data/exercise_images/<exercise_id>-0.jpg` / `-1.jpg`), declared once in
`pubspec.yaml`, and shipped in the app binary like the rest of `assets/data/`.

## Why a JSON manifest, not new DB columns

The original spec's `gif_url` / `gif_source` / `gif_source_id` columns assumed a
fetchable URL (remote or signed-storage). With images bundled as local assets
there is no URL to store — the "column" is really just "does this exercise ID
have a photo," which is a static, build-time fact, not per-user or per-row state
worth a database migration. That's captured two ways instead:

- `assets/data/exercise_images_mapping.json` — the full mapping (every exercise
  ID, match status, external source name/id, license) for auditability.
- `lib/features/workouts/presentation/widgets/exercise_photo_registry.dart` — a
  generated `const Set<String>` of exercise IDs that have photos, checked by the
  UI (`kExercisesWithPhotos.contains(exercise.id)`) to decide photo vs. animation.

Both are regenerated by the importer and never hand-edited directly (the
`CURATED`/`NOT_MAPPED` tables in `tool/import_exercise_images.py` are the actual
source of truth — see below).

## Matching methodology

An automated name/token matcher was tried first and produced two confirmed false
positives at >0.95 "confidence" (`barbell-back-squat` → `Barbell Hack Squat` on
character similarity; `push-up` → `Clock Push-Up` on a hyphenation-tokenization
mismatch). Given the task's explicit "never attach a potentially incorrect
image" requirement, automated scoring was abandoned in favor of hand-verifying
every candidate against the raw source dataset by exact-name lookup. The result
is the static `CURATED` (48 entries, tagged `auto` or `review`) and `NOT_MAPPED`
(13 entries, each with a stated reason) tables embedded directly in
`tool/import_exercise_images.py`. Re-running the fuzzy matcher would risk
reintroducing those same false positives, so the tables are meant to be hand-
edited and re-verified, not regenerated algorithmically.

## Gendered photos for the remaining 13

The 13 exercises free-exercise-db couldn't safely match (`diamond-push-up`,
`lunge`, `bulgarian-split-squat`, `glute-bridge`, `calf-raise`, `side-plank`,
`burpee`, `jumping-jacks`, `high-knees`, `kettlebell-swing`,
`chest-supported-row`, `single-arm-cable-row`, `cat-cow`) still fell back to the
vector stick-figure animation. Wikimedia Commons was tried first (public
domain/no-restrictions filter) and failed on the first two exercises checked
(burpee, jumping jacks) — results were military training photos, school gym
classes, and crowds/silhouettes, not the single-subject demonstration
photography free-exercise-db provided; Commons is an encyclopedic/historical
archive, not a fitness-stock-photo site.

**Decision (user-approved): [Pexels](https://www.pexels.com/license/) instead**
— free for commercial use, no attribution required, and it actually has posed
single-subject fitness photography. Each of the 13 exercises got one
male-presenting and one female-presenting photo, each picked by hand (viewing
the actual photo, not trusting a filename/keyword match) — same discipline as
the free-exercise-db curation. `ExerciseDetailCard` shows whichever matches the
active profile's `sex` (`other`/unset falls back to the male photo — both exist
and neither is more "default" than the other).

Same minimal-footprint approach as the rest of this doc: no new DB columns, no
new table. `assets/data/gendered_exercise_images_mapping.json` records the
Pexels photo id/photographer/license per exercise/gender for auditability, and
`lib/features/workouts/presentation/widgets/gendered_exercise_photo_registry.dart`
is the generated `const Set<String>` `ExerciseDetailCard` checks
(`kGenderedExercisePhotos`) before falling back to the vector animation. Both
are regenerated by `tool/import_gendered_exercise_images.py`; the `CURATED` dict
in that script (exercise id → Pexels photo id per gender) is the source of
truth, same pattern as `tool/import_exercise_images.py`'s own `CURATED` table.

```bash
python3 tool/import_gendered_exercise_images.py --download   # download missing images (skips existing files)
python3 tool/import_gendered_exercise_images.py --validate   # validate files
```

## Re-running the importer

```bash
python3 tool/import_exercise_images.py --dry-run                       # print the mapping, download nothing
python3 tool/import_exercise_images.py --download                      # download missing images (skips existing files)
python3 tool/import_exercise_images.py --validate                      # validate files + write exercise-gif-import-report.json
python3 tool/import_exercise_images.py --download --exercise plank     # scope to a single exercise id
```

Safe to re-run repeatedly: existing, non-empty files are skipped, and the
registry/mapping/report are regenerated fresh each run from the `CURATED` /
`NOT_MAPPED` tables.
